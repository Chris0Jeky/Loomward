# User experience and interface specification

## Tone and information hierarchy
The interface should feel like a workbench, not an alarm panel or a chat transcript controlling a disk. Show the current state, confidence/coverage, the best next decision and the cost of doing nothing. Use plain language while keeping technical evidence available. The guiding line is: **Intelligence proposes. You decide.**

Use a persistent mode indicator: synthetic demo, observed metadata, imported snapshot or future live managed session. A failed live connection must not silently display demo data. Unknown backing state must not acquire reassuring copy merely because a card looks better with a number.

## Current seven pages
**Overview:** logical indexed size, available disk space, feedback count, user-file changes and a proportional extension-family map. These metrics have different denominators. The current map uses real proportional area for the supplied snapshot; it is not the full hierarchical million-file treemap.

**Storage explorer:** filename/path search, extension-family filtering, logical size, flags, coverage counts and explicit duplicate inspection. Render at most 200 matching rows in the reference. The final design needs paginated/virtualised queries and drill-down aggregates rather than hiding this cap.

**Organise & learn:** existing virtual taxonomy, model suggestion, uncalibrated relative score, abstention and user label selection. Feedback is a separate action from future moving. The reference shows at most 100 review items and computes predictions for at most 2,000 snapshot items.

**Disk tiers:** capacity/reserve context, target free-space and transfer-budget inputs, availability/pin controls, simulated movements and remaining shortfall. Every current proposal is non-executable. The static demo's solver is intentionally limited to its fixture semantics; the Python planner is the testable reference.

**Processes:** read-only samples, memory and CPU semantics, optional refresh, missing permissions/dependencies as explicit messages. No disguised kill or RAM-trim buttons.

**Activity:** feedback events, provenance and persistence/export status. The current view shows the newest 200 profile events; full feedback export is separate and complete within the reference event budget. The audit chain is not a signed security log.

**Protection:** roadmap and unconfigured state. Do not present synthetic backup status as if the user's files were protected.

## Future review card
A proposed physical operation should show the exact group and number of objects; why it was suggested; alternatives; source and destination volumes; data read/copied/retained; when any space would actually be released; required backup/metadata guarantees; risk; current preconditions; and the recovery route. The approval button names the action, such as “Approve copying this project to Archive HDD,” not “Optimise.”

Expand a group to inspect its members. Show exclusions and unresolved dependencies prominently. A changed plan gets a new digest and requires new consent. Suggested destination names from a model must be mapped to user-approved destination IDs rather than being used as raw paths.

## Interactive questions
Ask at the semantic decision point. Examples: “Is this an invoice or project reference?” “Should these exports stay with the active project?” “Is this model pinned for your current coding session?” “Prefer fewer files moved, or more free space within the same transfer budget?” Show two or three meaningful options, including leave unchanged and defer. Do not repeatedly ask about a dismissed item every scan.

Feedback controls should include correct label, alternative label, defer, pin, exclude from inspection and explain uncertainty. Distinguish local browser-session feedback from persisted feedback. Standalone preview feedback must be exported before the tab closes; local-runtime feedback lives in SQLite.

## Accessibility and robustness
Use semantic headings, named buttons, keyboard focus indicators, a skip link, table headers, accessible live status messages, text equivalents to colour and reduced-motion support. Long filenames must not obscure actions. Tiny treemap cells remain available through text/table views. Validate imported snapshots before replacing the current view and escape all user-controlled display strings.

Test at 100%, 150% and 200% Windows scaling, high contrast, keyboard-only and Narrator. The current browser checks cover navigation, mobile width and hostile display strings, not full accessibility certification. The prototype uses system fonts and no external icon/font downloads.

## Information that should never be ambiguous
“Logical size” is not “disk space you will recover.” “No recent observations” is not “unused.” “Label saved” is not “file moved.” “Model suggests” is not “approved.” “Snapshot exists” is not “restore tested.” “App state written” is not “user-file mutation.” “Offline” is not “empty.” “Unverified build” is not “working native app.”

## Native integration path
Keep the UI's view models independent of HTTP. Replace the reference transport with typed Tauri/native IPC after Windows permission tests pass. Do not expose a broad filesystem or shell plugin just to reuse a button. The current Tauri directory is a synthetic preview shell scaffold, not an integrated daemon/ML client.
