# LW-136: Archive custody: copy count, rolling scrub and restore drills

Status: planned. Minted 2026-10-25 by the research programme (docs/51).
Milestone: M4. Priority: P1.
Dependencies: LW-124, LW-036, LW-084.
Owner question Q2 (docs/51 section 9) is open: a second copy on a rotated offline disk (recommended), cold cloud storage with a per-upload preview, or a single copy with a sole-copy warning in every plan.

## Scope
Make archive custody a product concept (docs/51 section 4.3, ADR R3). Each archived object carries its copy count, a manifest root (a per-directory Merkle tree with versioned collation) and `last_content_verified_at`, and a plan that would leave one copy says so. A rolling scrub verifies a bounded slice of `H:` each idle week, because one full pass of an 8 TB disk takes 12 to 19 hours (X6); an overdue scrub is shown as overdue, never as a failure. Restore drills (the G9 proven restore, LW-036) run on lab data placed on `H:`, never on the owner's archive contents. Scrubbing reads and the disk spins, but nothing is written or deleted.

## Acceptance evidence
Copy count and last-verification fields appear in every archive projection. A plan with one copy shows the sole-copy line. A scrub slice is bounded in bytes and time and resumes after an interruption. An overdue object shows as overdue, never as failed. The per-directory manifest root is stable under the versioned collation and changes when one byte changes (docs/51 section 2.2). A restore drill on `H:`, using lab data, restores the tree and compares it (docs/51 section 5 P4). Starting a scrub of the owner's archive waits for the owner's go-ahead (docs/51 section 10, X6).

## Notes
Duplicate check: LW-036 (backup restore verification and metadata fidelity) and LW-084 (backup evidence normalisation that does not equate success with recovery) are the nearest. This item adds copy count, the bounded scrub budget and the archive manifest root, which they do not own; LW-124 supplies the copy gate for the copies it counts. Once originals leave `C:`, `E:` or `G:`, `H:` is the only copy until a second copy exists (docs/51 section 4.3). PAR2 parity is deferred until a second copy exists (docs/51 section 6).

## Boundary
No additional capability is implicitly authorised by this issue. Keep file and process mutations, elevation, cloud
transfer of personal data and public release off unless the decision above and a named safety gate say otherwise.
Synthetic data only in Git.
